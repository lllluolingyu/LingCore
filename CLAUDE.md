# CLAUDE.md

Guidance for Claude Code when working in this repository.

## What LingCore is

A config-driven async agent framework. The same runtime becomes a different
agent type (coding, role-play, teaching, psych consultant) purely by loading a
different profile YAML — **adding a new agent type should be a config file, not
a code change.** That principle is the design's whole point; preserve it.

## Commands

```bash
uv sync                       # install deps (incl. dev group)
uv run pytest -q              # run the full suite
uv run pytest tests/test_config.py -q         # one file
uv run pytest tests/test_config.py::test_x -q # one test
uv run lingcore                               # launch the coding agent over CLI
uv run lingcore doctor -p profiles/coding     # offline profile/env diagnostics
uv run lingcore plugin list -p profiles/coding
uv run lingcore plugin info canvas -p profiles/coding
uv run lingcore plugin new hello -p profiles/coding
uv run ruff check                           # lint
uv run ruff format --check                  # formatting
uv run mypy                                # package-wide types
uv run lingcore --profile path/to/p.yaml      # launch a specific profile
uv run lingcore --workspace /path/to/dir      # override workspace from the command line
uv run lingcore --list-sessions               # list stored sessions for the profile, exit
uv run lingcore -c                            # resume the most recent session
uv run lingcore --resume <id-prefix>          # resume a session by unique id prefix
uv run lingcore --no-session                  # run without persisting this session
uv run lingcore telegram -p profiles/coding   # run the official Telegram channel
uv run lingcore doctor -p profiles/coding --telegram-config path/to/telegram.yaml
```

Run pytest, Ruff lint/format checks and mypy in both LingCore and LingChat.

## Architecture (where things live)

Dependency flows bottom-up; `message.py` depends only on the stdlib-only
`media_types.py`, the loop depends on everything below it, frontends depend
only on `Agent` + events.

- `lingcore/media_types.py` — stdlib-only attachment validation rules (extension+magic-byte allowlist, size caps, name sanitization) shared by the message model; deliberately imports nothing from the rest of LingCore.
- `lingcore/message.py` — `Message`/`ToolCall`/`ToolResult`/`Attachment`/`UserInput`/`Conversation`. A stored user `Message.input_text` retains the accepted user-authored text separately from model-facing attachment ingest notes, plugin context and slash-command expansions. `UserInput.display_text` retains the typed command. `Message.to_openai()` is the **only** place that knows the chat-completions wire shape — including the modality-narrowing render (`attachment_modalities=` parameter, see invariant 15).
- `lingcore/media.py` — attachment construction helpers for tools/frontends (`attachment_from_path`/`attachment_from_wire`/`classify_bytes`); converts validation failures to `ToolError`. **Any file attaches**: `classify_bytes` sorts bytes into the four `Attachment` kinds — native `image`/`file` (extension+magic agree), `text` (NUL-free **and** UTF-8-decodable), or `binary` (everything else).
- `lingcore/paths.py` — stdlib-only confinement primitives. `resolve_confined(base, rel)` + `PathEscapeError` handles read/static path validation (`resolve()` collapses `..`/symlinks before containment). Security-sensitive state uses `confined_directory`: it walks intermediate components with `dir_fd` + `O_DIRECTORY|O_NOFOLLOW`, holds the validated parent descriptor through the operation, and exposes `ConfinedDirectory` operations for no-follow entry enumeration (`iter_entries`), descriptor-relative child-directory opening (`subdirectory`), bounded no-follow reads, exclusive create, no-follow stat/unlink, and descriptor-relative atomic replace. Thus replacing a validated parent with a symlink cannot redirect ingest payloads, `attachments/.gitignore`, Canvas `.part`/destination writes, staged tool output, search traversal, or the serialized knowledge index. Platforms without the required secure descriptor operations fail closed instead of falling back to pathname I/O.
- `lingcore/ingest.py` — `ingest_attachments`: the agent-side step that copies every user attachment into `<workspace>/attachments/` (collision-safe), inlines a `text` file's content / writes a `binary` pointer note as `fallback_text`, and returns note lines announcing each path. **Never raises** (a failed copy degrades to a note); image/PDF fallbacks stay with `MediaAdapter`. Called from `Agent.run` via `asyncio.to_thread` (blocking I/O) before `MediaAdapter.prepare`.
- `lingcore/modality.py` — `MediaAdapter` + `extract_pdf_markdown`: text fallbacks for the **convertible** kinds (`image`/`file`) the model doesn't accept (`llm.modalities` registration + `media_fallback` config); `text`/`binary` are skipped (ingest owns their fallbacks). Takes a duck-typed vision client; never imports `llm.py`/the SDK. pymupdf is loaded lazily (optional `lingcore[pdf]` extra).
- `lingcore/llm.py` — `LLMClient`, the single seam over the OpenAI SDK. All streaming quirks (index-keyed tool-call fragment reassembly, partial-JSON args) live here. Transient-failure retry is **two-tier**: *opening* the stream is delegated to the SDK's header-aware policy (honors `Retry-After`/`retry-after-ms` and `x-should-retry`; retries 408/409/429/5xx + connection/timeout), bounded by `max_retries` and a per-attempt `timeout` from config. Once the stream is yielding the SDK never retries, so the client *classifies* instead: every failure raises a typed `LLMStreamError` (`lingcore/errors.py`) — `retryable=True` for mid-stream interruption/stall/truncation (incl. a stream ending without a `finish_reason`), `retryable=False` once the SDK's open budget is spent or the request is invalid. The *loop* owns recovery (`llm.stream_retries`, see invariant 5); tokens are never silently replayed — a retry discards the partial turn and announces itself via a `StreamRetry` event. Opt-in `llm.preserve_reasoning` (thinking-mode providers such as DeepSeek) makes the client yield streamed `reasoning_content` as `LLMChunk.reasoning_delta`, which the loop stores on the assistant `Message.reasoning_content` (persisted with the message, counted by `WindowMemory`, never shown as reply text); `to_openai(include_reasoning=True)` then echoes it on every assistant message — `""` when none was recorded — because DeepSeek rejects a tool-bearing request whose assistant messages omit it. Off by default so strict servers never see the field. Opt-in `llm.send_prompt_cache_key` makes the client send `prompt_cache_key=<session_id>` so same-session requests route to the same warm prompt-cache node (off by default; a strict OpenAI-compatible server may reject the field).
- `lingcore/events.py` — `AgentEvent` union the loop emits (incl. `SkillActivated`, `Compacted`, `TurnCancelled`, `UsageReported`, `TodoUpdated`, transient `PluginNotice`).
- `lingcore/todos.py` — pydantic-only `TodoItem`/`TodoState` + validation/render/payload helpers for `todo_write`. The live `TodoState` is shared via `ToolContext.options[TODO_STATE_KEY]` (like `SkillState`); the loop snapshots it in the turn checkpoint, diffs it around each tool batch, persists `todo_state` session events and yields `TodoUpdated`. It is deliberately **never** composed into the system prompt (a changing list there would bust the cached prefix); tool results carry it, and the memory's `set_pinned_note` (refreshed every iteration) makes compaction append it verbatim to the summary and eviction re-insert it as one synthetic `name="pinned"` message at the retained head, so the model never loses the list while `TodoState` holds it.
- `lingcore/usage.py` — SDK-free `TokenUsage` + `UsageMeter` + the OpenAI-shaped usage parser. Counts follow the chat-completions convention (`input_tokens` includes cached, `output_tokens` includes reasoning); LingCore never estimates them.
- `lingcore/agent.py` — the async run loop + `Agent.from_profile`. The core.
- `lingcore/composer.py` — `PromptComposer` protocol + `ComposeContext` + `StaticComposer`/`LayeredComposer`. The per-turn system-prompt assembly seam. `read_project_instructions` loads the first `persona.project_instructions` workspace file (e.g. `AGENTS.md`) each compose via `confined_directory` no-follow reads, bounded in bytes and chars; it never raises.
- `lingcore/config.py` — `AgentProfile` (+ `skills:` static declaration and explicit `plugins:` consent) + nested pydantic cfgs; exact profile-local `.env` parsing (literal, non-interpolating — a `${` in a secret survives verbatim) followed by YAML `${ENV}` expansion; `_source_dir` / scoped environment resolution.
- `lingcore/sandbox.py` — typed host/Bubblewrap/OCI shell runners, fail-closed backend selection, guest environment injection, resource/mount policy, process supervision, and OCI cleanup watchdog integration.
- `lingcore/outer_agents.py` — shared support for the bundled `codex`/`claude-code` skills: `OuterAgentSpec` (tool name = `tool_options` key, PATH program, label, state namespace; `OUTER_AGENTS` lists the bundled specs for `doctor`), the shared `OuterAgentArgs`/`frame_prompt` brief, `run_outer_agent` (bounded capture, timeout/cancel → process-group kill+reap via the sandbox helpers, non-zero exit → `ToolError`), `render_outer_agent_reply` (offload like builtins), and conversation aliases (`load/save_conversation_session`, `conversation_lock`) confined under the profile dir and scoped by `(workspace, session_id)` — `session_id=None` degrades to a workspace-wide scope. Skill modules keep only what differs per CLI (session establishment, output parsing, and hardened non-interactive flags: Codex pins the human approval reviewer; Claude disables customizations/MCP and runs restricted in both modes).
- `lingcore/doctor.py` — offline/read-only profile diagnostics: required environment names and sources, profile-first empty-value semantics, manifest-driven plugin/opt-in knowledge checks, outer-agent option validation + CLI resolution (no subprocess), and secret-free `.env.example` coverage. Never prints values or builds an agent.
- `lingcore/knowledge.py` — provider-independent `EmbeddingProvider`/`RerankingProvider` protocols plus the SiliconFlow HTTP adapters/builders. Secrets are resolved from the env var named by `api_key_env` only after the explicit retrieval opt-in.
- `lingcore/memory.py` — `ShortTermMemory` protocol + `WindowMemory` + `SummarizingMemory`. `WindowMemory` eviction is **prefix-stable** (whole oldest blocks are evicted in one chunk down to `evict_to_ratio` only when a hard cap is breached, so the rendered prefix stays byte-stable across turns → prompt-cache hits; invariant 6). Encoding selection is lazy and reads only encodings already loaded in tiktoken's process cache; otherwise counting falls back to a deterministic UTF-8 byte-ratio estimate without vocabulary downloads. Eviction is **physical**: evicted blocks are removed from the retained list (and `_floor` counts them, monotonically), so retention is bounded by the window, not the whole conversation. `SummarizingMemory` composes a `WindowMemory` and adds the **compact-then-evict** policy (`maybe_compact`, called once per turn): summarize the oldest history via a duck-typed summarizer when nearly full, else fall back to eviction.
- `lingcore/sessions.py` — `SessionStore` (SQLite, one db per profile dir) + `SessionMemory` (a `ShortTermMemory` wrapper that records every message and compaction snapshot) + `trim_dangling`/`attach_session`/`open_store`. Stable message sequences plus a monotonic, message-anchored runtime event log persist bounded, canonical-tail-validated compaction snapshots and consent-aware dynamic skill state; truncate/rewind remove both the transcript branch and its derived events for frontend Stop/Edit. `fork_session` atomically copies a validated prefix and its compatible events under `BEGIN IMMEDIATE`, reminting cursor ids and recording lineage in `sessions.meta`. Composition roots open the store while `Agent.from_profile(session_store=..., session_id=...)` wires it.
- `lingcore/skills.py` — `Skill`/`SkillState`/`load_skills`/`load_skill_tools`. The skill permission model + the loader that imports a skill's shipped tool code.
- `lingcore/guardrails.py` — `Guardrail` protocol + `NoopGuardrail` + profile-selected dotted-path/`lingcore.guardrails` entry-point loader.
- `lingcore/profiles.py` — explicit immutable template manifest and atomic initialization into writable user application state.
- `lingcore/tools/__init__.py` — `Tool`/`@tool`/`ToolRegistry`/`ToolContext` (the plugin contract).
- `lingcore/tools/builtin/{fs,git,patch,shell,web,memory,knowledge,skill,todo,pdf}.py` — builtin tools (`pdf.py` = the `pdf2md` extractor, optional-dependency-gated). `git.py` provides structured read-only status/diff/log/show/branch inspection without shell approval and refuses parent checkouts, linked/separate worktrees, and alternate object stores; all mutating or networked Git remains confirmation-gated shell work. `fs.search` runs its explicit sorted walk in a worker thread, prunes configured directory names, supports scoped literal/regex/case-insensitive content and recursive filename lookup, enforces time/file/depth/hit/context budgets (including timed regex matches with partial-result reporting), reads candidates through confined no-follow regular-file descriptors, and reports deterministic coverage. `knowledge.py` keeps grep as the offline default and owns deterministic chunking plus its incremental SQLite FTS/vector store; embedding and reranking are separately opt-in. Output is kept cache-friendly: `read_file` is paginated + line-numbered (`offset`/`limit`), `list_dir`/`search`/`knowledge`/`git` are capped and deterministically ordered, and `_offload.py:offload_text` stages oversized `search`/`run_shell`/`fetch_url` output with no-follow directory descriptors and a descriptor-relative atomic replace at `<workspace>/.lingcore/tool-output/<source>-<hash>.txt` (read the rest with `read_file`), degrading to truncation on write failure — never raises.
- `lingcore/io/{base,cli}.py` — frontend protocol + `run_session` driver + Rich CLI. The CLI streams replies as markdown (completed blocks are committed to scrollback; the block in progress and a working spinner live in one transient `Live` region, disabled off-TTY) and, on a TTY, reads input through a prompt_toolkit editor (Enter sends; Shift/Alt+Enter, Ctrl-J or `\`+Enter insert a newline; history; slash-command/`@path` completion) with a bottom status bar built only from frontend-known state and `UsageReported` events. Off-TTY (pipes, tests) it falls back to `console.input` in a worker thread. `run_session` drives each turn in its own task; a frontend may expose `interrupt_scope(stop)` (the CLI maps the first Ctrl-C to `Agent.cancel_turn`), after which `run_session` finalizes and renders the drained usage then `TurnCancelled`. CLI slash commands `/new` and `/resume` are carried back to `__main__` as a `SessionSwitch`, which rebuilds the agent with fresh deep-copied tool options.
- `lingcore/integrations/telegram/` — official Telegram channel. Config, bridge
  state, per-user runtime isolation, rendering, confirmations, and attachment
  conversion are PTB-light; only `application.py` imports
  `python-telegram-bot` and owns handler registration/runners.
- `lingcore/__main__.py` — the CLI entrypoint / composition root.
- `profiles/coding/` — the checkout's default profile dir (`config.yaml` + world/role/workflow `.md`). Source profiles live at the **repo root, outside the package tree**; wheels carry immutable template copies that `lingcore profile init` moves into user state before use. In both cases `sessions.db`/`memory.md`/the default `workspace/` stay writable and outside installed code.
- `profiles/coding_ollama/` — Ollama/vLLM variant (keyless local server).
- `profiles/daily/` — general-purpose assistant (research/notes/memory, no shell).
- `profiles/teaching/` — teaching assistant; statically engages the `canvas` skill (`skills: [canvas]`).
- `lingcore/skills/` — instruction-only core skills (`code-review`); profile-local skills may still ship Python (`module:` + `provides:`).
- `lingcore/plugins/` — strict manifests, data-only discovery, engagement, atomic loading, the stable API v1 hook runner, command catalog and scaffold creation.
- `lingcore/bundled_plugins/` — first-party Canvas, Codex, Claude Code and Browser manifests, tools, skills and variable-name templates; existing profiles auto-engage their tools/skills. `browser/` (optional `lingcore[browser]` Playwright extra, imported lazily) keeps one ephemeral headless Chromium per Agent inside its `BrowserHooks` instance, so its tools require `plugins: [browser]`; it returns AI-mode aria snapshots with `[ref=eN]` element handles. Playwright routing validates each request URL with `fetch_url`'s `_vet_url` rules, and Chromium connects only through a per-session loopback SOCKS5 proxy that vets and pins every connection (redirect hops included), configured by the shared `NetworkPolicy` (`tool_options.py`). One `BrowserHooks` lock serializes tool calls with `browser_close`/`aclose`, and closing runs as an owned task that resumes after cancellation.

## Invariants — do not break these when extending

1. **The loop never imports `openai` directly.** `agent.py` talks only to an `LLMClient`-shaped object (duck-typed `.stream()`). This seam is what lets a different backend (or LangGraph) swap in later. Keep OpenAI specifics inside `llm.py`.
2. **Tools get context as a parameter (`ToolContext`), never via mutable LingCore globals** — so concurrent sessions with different workspaces and profile-local environments stay isolated. A tool that needs an environment value uses `ctx.getenv(name)`: that context's parsed profile `.env` wins, then the exported process environment is the fallback. Secret values stay in `ToolContext.environment`, never in the generally copied/mutated `options` dict.
3. **Frontends consume `AgentEvent`, never LLM internals.** `PluginNotice` is transient, is rendered by each frontend, and arrives before the corresponding terminal event; it is never stored as conversation history. Frontends close plugin instances on Agent replacement and shutdown through `Agent.aclose`. Every model request an agent makes on a turn's behalf — the visible reply, the compaction/memory summary, the vision fallback — reports provider usage into the agent's one `UsageMeter`, which `run()` drains into `UsageReported` events *before* the event that followed the request (so usage always precedes the terminal event); a frontend that doesn't account for spend ignores them, and a Stop-aware one calls `drain_usage()` after finalization to collect what was billed before cancellation landed. Usage is never estimated: a request whose stream died before its usage block simply has none. `run_session` is frontend-agnostic; new frontends implement the `Frontend` protocol and change nothing else. A frontend that supports Stop cancels the task driving `Agent.run`, awaits it, then calls `finalize_cancelled_turn()` and renders its `TurnCancelled` event; partial assistant/tool conversation state is void in memory and SQLite, while the exact committed user row remains. The checkpoint stays leased until finalization, so neither a same-task re-entry nor a newly started task can overwrite rollback state.
4. **Secrets never live in profile YAML or a skill directory.** `llm.api_key_env` / skill `token_env` settings only *name* variables. Real local values may live in the selected profile's gitignored `.env`; `AgentProfile.load` parses only the exact file beside the selected YAML (no CWD/parent discovery), before `${ENV}` expansion, and keeps the result profile-scoped rather than mutating `os.environ`. The explicitly selected profile's `.env` takes precedence over same-named exported variables; even an empty profile value blocks ambient fallback and is treated as unset — everywhere: key resolution fails loudly, `ToolContext.getenv` returns the caller's default, and a YAML `${VAR:-default}` expansion falls back to its default. Commit secret-free profile `.env.example` files whenever runtime environment names are required; a skill may additionally carry a generic declaration, but real values remain profile-owned. `lingcore doctor` checks names/sources and example coverage without printing values or producing runtime state. Profiles use `extra="forbid"` so a typo is a loud `ConfigError`; errors and reprs must never expose secret values.
5. **Tool errors never crash the loop** — a raising tool becomes `ToolResult(ok=False)` fed back to the model. Hard `max_iters` cap emits an `Error` event rather than raising. **LLM failures don't crash it either**: a retryable `LLMStreamError` makes the loop discard the partial turn (it was never committed to memory/session), emit `StreamRetry` so frontends can void any rendered text, back off with jitter, and re-request — up to `llm.stream_retries` times per request. Terminal failures (non-retryable, budget exhausted, or a foreign exception from a duck-typed client) end the turn with an `Error` event; `run_session` never sees an exception from a model failure.
6. **`WindowMemory` eviction is block-aware, prefix-stable, physically bounded, and offline-safe.** An assistant `tool_calls` message and its `tool` results are atomic; never orphan a tool result from its call (OpenAI rejects it), and always keep ≥1 block. Encoding lookup is lazy (never part of `WindowMemory.__init__`/agent assembly) and uses only an encoding already loaded in tiktoken's process cache; otherwise counting permanently falls back to a deterministic UTF-8 byte/4 estimate for that window. Rendering never downloads vocabularies, even with a cold disk cache, and special-token spellings in input are counted as ordinary text. Eviction is **hysteretic**: whole oldest blocks are dropped only when a hard cap is breached, in one chunk down to `evict_to_ratio` of the token budget. Between evictions the rendered list is append-only, so consecutive requests share a byte-identical prefix and the prompt cache hits — *the* reason within-turn tool iterations don't thrash the cache (`evict_to_ratio=1.0` restores the legacy slide-every-render). A `set_pinned_note` is rendered only at an eviction (inserted as one synthetic head message, with room reserved for it) or a compaction (appended to the summary), never per request, so a changing note cannot break that prefix. Eviction is **destructive**: evicted blocks are removed from the retained list (their `Message` objects, incl. attachment payloads, are released), and `_floor` accumulates the lifetime count of evicted blocks (monotonic) — retention is bounded by the window, not the whole conversation. `SummarizingMemory` layers **compaction** in front: at a turn boundary, when the working set is nearly full, it summarizes the oldest blocks into one note (keeping the recent tail verbatim) via a duck-typed summarizer and resets the counter; if still over the hard cap, eviction finishes the job. Compaction runs **once per turn (never mid tool-loop)** and rewrites only the working set. `SessionMemory` persists that derived working-set snapshot at the current transcript watermark while keeping the canonical transcript lossless; resume restores the newest valid snapshot and only replays the raw tail after it (see invariant 14).
7. **`run_shell` is arbitrary code execution with independent confirmation and isolation policy.** The `confirm` gate controls whether a command may run; `tool_options.run_shell.sandbox` selects an optional OS boundary. Omitting it retains the explicitly labelled legacy host runner, where cwd is not confinement and shell can escape the workspace. Configuring Bubblewrap or OCI is fail-closed: launch/setup failures never fall back to the host. The bundled coding profiles select Bubblewrap (empty root, explicit read-only system/mount exposure, private namespaces, and networking off by default); OCI uses a fresh non-root container with mandatory resource budgets and watchdog-backed removal. Bubblewrap bounds `/tmp` but has no LingCore-managed CPU/memory/PID cgroup budget. Every runner has timeout-with-process-group-kill (a per-call `timeout` argument is clamped to `run_shell.max_timeout`, which defaults to `timeout`) **and the same kill+reap on `CancelledError`**; cleanup failure never replaces the primary cancellation, timeout, or exit-code diagnostic, while an OCI removal failure leaves the watchdog armed. Output is **read into a bounded in-memory cap** (drains the pipe past the cap so the child can't deadlock, but never buffers unbounded) then offloaded/truncated. The optional allowlist uses **exact-or-prefix matching**: a bare single-token pattern (e.g. `cat`) matches only itself, while a multi-token pattern deliberately authorizes that token prefix plus trailing arguments. Shell control syntax (`;`, standalone `&`, `&&`, `||`, pipes, redirects, substitutions, grouping, or newlines) is never auto-approved, so a prefix cannot be extended into another shell command. No allow patterns ship by default.
8. **An unset `workspace` defaults to `<profile dir>/workspace/`** (auto-created at assembly; gitignored for bundled profiles) — a bare launch never adopts whatever directory the user happened to be in. **An explicit relative `workspace` resolves against the user's CWD** (where they launched lingcore), not the profile's directory. Bundled profiles write `workspace: ${LINGCORE_WORKSPACE:-}`; the blank expansion is normalized to *unset*, so the env override stays available without changing the default.
9. **Network fetch is public-web only by default.** `fetch_url` rejects embedded credentials and non-http(s) schemes, resolves the host and rejects any answer that maps to a loopback/link-local/private/reserved address (covering alternate IP encodings — decimal/hex/octal), then **pins the connection to the vetted IP** while keeping the Host header and TLS SNI/cert verification on the hostname — so DNS can't be rebound between the check and the connection. Re-applied to every redirect hop; DNS resolution and downloaded body size are both bounded. A blocked target is put to the user through `ctx.confirm` (once per host+address per fetch, including redirect hops; the approved address stays pinned) and refused on denial, with no handler, or with `confirm_private_hosts: false`. Frontends tell such prompts apart from shell ones by tracking the turn's `run_shell` commands — only those get the shell framing and "always allow". Opt into local targets without asking via `tool_options.fetch_url.allow_private_hosts: true`. `tool_options.fetch_url.allowed_networks` (CIDR list, validated at profile load) exempts only the listed ranges and keeps pinning — meant for TUN-mode fake-IP proxies whose DNS answers come from the `198.18.0.0/15`/`2001:2::/48` benchmarking ranges; the block error and approval prompt name that cause. The exemption trades away detection of hostnames whose real address is private (the proxy resolves them); IP literals and `localhost` stay refused. The policy keys (`allow_private_hosts`, `confirm_private_hosts`, `allowed_networks`) are one strict `NetworkPolicy` parsed from `tool_options.fetch_url` at profile load — a stringly `"false"` is an error, never truthy. The bundled browser plugin reads that same policy (the keys are rejected under `tool_options.browser`) for every request a page makes, aborting non-public ones; only `browser_navigate` may ask, approving that hostname for the browser session. Browser connections go through the plugin's vetting SOCKS5 proxy, which resolves names and pins the vetted address like `fetch_url`.
10. **The system prompt is composed per loop iteration, not frozen.** `agent.py` calls `composer.compose(ctx)` at the top of *every* iteration with an immutable `ComposeContext` (never mutable hidden state). This is why memory writes and skill activation take effect on the *next* model request. A `StaticComposer` (no layers/memory/skills) is the zero-overhead default; `LayeredComposer` reads memory.md fresh each call. Composer content is **read-only context — it can never unlock a tool.**
11. **Skills and plugins never grant tools beyond the profile; the profile has three tool tiers.** Plugin registration does not authorize a tool. Hook allow decisions continue the chain and preserve each tool's own confirmation; deny/ask can only add friction. Plugin upgrades have no wildcard ceiling entries. `tools:` is the hard **ceiling**. The set enabled with **no skill active** defaults to *all* of `tools` and is narrowed by exactly one of two forms — `initial_tools:` (inclusion list) or `skill_gated_tools:` (exclusion list: the ceiling minus these; prefer it when only a few tools are gated so a tool later added to `tools` isn't silently gated) — resolved by `AgentProfile.initial_tool_set()`; declaring both is a `ConfigError`. Narrow it to gate the rest behind skills (progressive disclosure / least privilege). When a skill is active it unlocks `profile.tools ∩ skill.requested_tools` on top. A *statically-engaged* skill (`skills:`) is always on: its requested∩ceiling tools are folded into the initially-enabled set at assembly — naming the skill in the profile is operator consent, so the high-risk confirm gate (which guards *model-initiated* activation) does not apply there. A tool that is neither initial nor granted by an active skill is neither advertised (`_effective_tool_schemas`) nor dispatchable (`_resolve_tool` raises the unknown-tool error) — the ceiling and the initial/skill gate are both enforced in each. Dispatch snapshots authorization once for the whole model-produced tool batch, so activation/deactivation affects the **next** model request and can never unlock or revoke a sibling call in the current batch. `activate_skill` mutates only the shared `SkillState.active`; the base `ToolRegistry` is **never** mutated. High-risk tools require `confirm` before activation — and if a skill requests one but **no confirmation handler exists, activation is refused** (never silently activated, mirroring `run_shell`). The high-risk set is the name-based builtin baseline `DEFAULT_HIGH_RISK_TOOLS` (`run_shell`/`write_file`/`patch_file`/`edit_file`; `tool_options.activate_skill.high_risk_tools` replaces this baseline) **unioned with every authorized tool that declares `@tool(high_risk=True)`** — a tool's own declaration is a floor the override cannot lower, and it is how skill-shipped tools (e.g. `codex_agent`) stay gated without `skills.py` ever naming them. The exact high-risk grant set covered by that confirmation is recorded with the activation; resume refuses the skill if its current risky grants are wider, and schema/dispatch authorization independently filters any risky grant absent from the recorded set. `activate_skill` only *offers* skills the profile can actually use (≥1 requested tool authorized, or instruction-only).
12. **`memory` writes are profile-scoped and confined.** The memory file resolves against `profile_dir` (not the workspace); relative paths that escape it raise `ConfigError`, absolute paths require `allow_absolute_path: true`, and writes into the installed package tree are refused **for both relative and absolute paths** (`allow_absolute_path` is not a package-write hole). `max_bytes` is checked on the *final* file content. Strict keys: `remember` fails if the key exists; `modify`/`forget` fail if it doesn't. **Opt-in auto-compaction** (`tool_options.memory.auto_compact`): when a write pushes the file past `compact_at_ratio × max_bytes`, the tool condenses `memory.md` with a duck-typed summarizer (injected via `MEMORY_SUMMARIZER_KEY`, the same `stream` seam — no `llm.py` import) instead of hard-failing; the `max_bytes` check remains the fallback guard, and condensation can merge/rename keys (the model re-reads via `action="read"`). Off by default → the hard-fail behavior is unchanged. The composer resolves the memory-file path from the *effective* (caller-overridden) tool options and honors an allowed absolute path, so the injected memory matches where the tool writes.
13. **Skill and plugin modules load atomically; the `tools:` ceiling still governs.** `_load_tool_module` is the shared file loader called before `REGISTRY.subset(profile.tools)`. It rejects declared collisions before execution, detects undeclared registrations and incumbent overwrites by object identity, checks missing registrations, and rolls back the registry and synthetic module on failure. Synthetic identities use resolved paths, so local shadowing cannot alias already-loaded code. Core/profile skill modules load only for static engagement or a provided tool in the ceiling. Plugin-owned modules additionally enforce the plugin prefix, including skill modules. Catalog order is core skills, visible plugin skills, then profile `skills_dir`; local skills can shadow plugin skills (a shadowed skill and tools the local skill provides never auto-engage the bundled code), while duplicate skill names between visible plugins, or a plugin skill reusing a core skill name, are errors. Registration never mutates an Agent's runtime ceiling.

14. **`sessions.db` is profile-scoped and confined exactly like memory.** The session DB resolves against the profile dir; a relative `sessions.path` that escapes it raises `ConfigError`, an absolute path requires `sessions.allow_absolute_path: true`, and a path inside the installed package tree **gracefully disables** persistence with a one-line notice — never an error, since sessions default to enabled. Bundled profiles live at the repo root (`profiles/`) precisely so this rule doesn't bite them; LingChat surfaces the notice in its sidebar (the `notice` field of `GET /api/sessions`) instead of hiding the feature. Session rows are **lazy**: the row is created in the same transaction as the first message, so an opened-but-silent session (instant `/exit`, browser reconnect loop) leaves no empty rows behind. Loading for resume is block-aware: `trim_dangling` drops any assistant message whose `tool_calls` lack complete tool results (anywhere in the list — a crashed turn can leave one mid-list once later turns append after it) and orphaned tool results, but keeps a trailing lone user message (valid prefix, real input). Schema v2 adds `session_events`: compaction snapshots, complete dynamic skill transitions (including approved high-risk grant sets), and complete `todo_state` checklists are anchored to stable message sequences and assigned AUTOINCREMENT ids. Resume considers full snapshots newest-first, accepts one only when its synthetic-summary shape is valid and its remaining messages exactly match a complete canonical transcript suffix, replays only later raw messages, and restores the validated assistant turn count. Only the two newest full snapshot bodies survive; older compact metadata/cursors remain, and forks apply the same bound. Skill restore filters through the profile's *current* offerable set/permission ceiling and refuses risky grant drift (non-concurrent mode keeps only the last); a corrupt latest state fails closed instead of reviving an older activation. Corrupt derived events never brick the canonical transcript. Stop uses the exact sequence returned by the user's append transaction, keeps that row, and atomically removes its assistant/tool tail plus runtime events anchored to the canceled turn; Edit accepts only an ordinary user row, deletes that row and everything after it, preserves its original attachments for regeneration, then rebuilds from the surviving snapshot/state. Event ids are never reused after branch deletion, so frontend cursors can replay replacements deterministically. `fork_session` is a profile-local, eager conversation copy: it validates the inclusive prefix as a complete tool-call history, copies canonical messages and only compatible anchored events in one `BEGIN IMMEDIATE` transaction, assigns fresh event ids, and stores immediate-parent/root/through-seq provenance. Forking never mutates the source. It does **not** fork the workspace or reverse tool side effects; both branches share those external files, and attachment payloads are duplicated in SQLite. Conversation rollback likewise cannot undo an external side effect from a tool that finished before Stop. Per-session "allow always" shell patterns remain deliberately ephemeral (re-approval is conservative), and attach-exclusivity (LingChat's one-tab-per-session rule) is per-process only.
15. **Attachment modalities are config-registered; degradation never crashes the loop.** Attachments have four kinds: `image`/`file` can ride **natively**; `text` always inlines its UTF-8 content; `binary` is an opaque file the model reaches only through workspace tools. A `text` attachment must be **valid UTF-8** (NUL-free *and* decodable) — `validate_text_payload` rejects a mislabeled binary at validation rather than inlining replacement characters. `llm.modalities` (typed to the native subset — declaring `text`/`binary` is a loud `ConfigError`) declares which native kinds the model accepts (default: both `image` and `file`). **Every user attachment is copied into `<workspace>/attachments/` at ingest** (`ingest_attachments`, collision-safe, using `confined_directory` for no-follow parent traversal and descriptor-relative exclusive creation so final symlinks and concurrent parent swaps cannot redirect the write) and its path announced in the user message text, so workspace-confined tools can reach it. Fallbacks are split by who can compute them: `ingest` sets `text` (inlined content, capped at `TEXT_INLINE_MAX_CHARS`) and `binary` (a workspace pointer note) fallbacks; `MediaAdapter.prepare` sets `image`/`file` ones when the model lacks that modality (PDF → extracted markdown, image → a `media_fallback.image` vision description) and **skips** `text`/`binary`. Both run **once at ingest**, before the message is committed, and **never raise** — failures (a missing pymupdf, a failed copy) become diagnostic notes the model can read. Originals are never stripped: sessions/LingChat keep full payloads, so raising `modalities` later restores native delivery, and `model_copy` keeps validators out of the hot path. The native-vs-text decision happens per render in `Message.to_openai(attachment_modalities=...)` (the `LLMClient` passes its set; `text`/`binary` are never in it); when **no native part remains the content collapses to a plain string** — text-only servers may reject a parts array. The describe call goes through the same duck-typed `stream` seam as the main model and always renders natively (config validation rejects a vision model whose own `modalities` exclude `image`).
16. **Knowledge embedding is explicit opt-in; grep stays offline.** `tool_options.knowledge.backend` defaults to `grep` and the separately checked `embedding.enabled` flag defaults to `false`; status/grep never resolve a provider key or make a network call. `index`/`hybrid` require the opt-in and receive an `EmbeddingProvider` through `ToolContext` (the SiliconFlow builder is only the default composition), keeping the local store vendor-neutral. Provider YAML only names `api_key_env` — literal key material is never accepted; the builder resolves the exported/profile-scoped environment carried by that `ToolContext`. The index is confined to the workspace (default `.lingcore/knowledge.sqlite3`), excludes LingCore runtime artifacts from its corpus, chunks deterministically with path/page/line metadata, reuses normalized vectors by content hash, and removes deleted sources on a full build. Because SQLite cannot consume an already-open no-follow descriptor, the database is bounded-read into memory with `ConfinedDirectory.read_regular` and serialized back through `open_exclusive` + descriptor-relative atomic replace; it never reopens an attacker-swappable workspace pathname. Index updates hold a persistent, descriptor-confined per-index advisory lock across load, embedding, and publication; acquisition is nonblocking and cancellable, and both tasks and processes serialize without deleting the lock file. Query-time size/mtime **and content-hash** checks exclude changed/deleted documents until reindexing, so a citation never knowingly points at stale text. Embedding/reranking and returned context all have hard batching/candidate/output caps; optional PDF indexing degrades to a reported skip when the PDF extra is absent.

17. **Telegram is a single-process, per-user-isolated channel.** Only allowlisted numeric users in private chats reach an Agent. Every user gets a deep-copied profile/tool-options tree plus a separate workspace, memory file, and sessions database beneath the configured state root; `bridge.sqlite3` stores the explicit active session across restarts, while an invalid selection is logged value-free and treated as absent so a successfully built fresh runtime can overwrite it. PTB imports stay inside `lingcore.integrations.telegram`, and ordinary CLI/doctor imports remain usable without the extra. PTB update dispatch stays explicitly serialized; its rate limiter retries one `RetryAfter`. Background turns use `asyncio.create_task` (not PTB's task registry), so Stop/shutdown can cancel, await, and finalize them without PTB waiting indefinitely. A Telegram render/send failure never closes the Agent stream: the bridge logs only exception types (download/request errors may contain the bot-token URL), keeps consuming events, and makes a bounded best-effort plain terminal delivery. Update/album deduplication is bounded and in-memory, so it does not bridge process restarts. Telegram refuses `run_shell` unless every call requires confirmation and the auto-approval list is empty.

18. **Plugins require consent and can add only friction or context.** Discovery reads bundled, installed entry-point and profile-local manifests without importing plugin code; later sources shadow earlier ones visibly. A broken installed/local plugin is skipped and reported, failing only a profile that enables or engages it. `plugins:` names are explicit consent to execute third-party code. Bundled skills stay visible and bundled code may auto-engage through a named skill or authorized provided tool, preserving existing profiles, but hooks/commands/prompt layers always require explicit enablement. API v1 hooks have one instance per Agent, ordered bounded calls, recursively frozen context/options/events, scoped getenv, fail-closed defaults and cancellation propagation. before_tool runs only after authorization and validation, with a fixed batch snapshot. after_tool patches content before commit and cannot change identity, success or attachments. user_message blocks before any user-memory/SQLite commit. Agent.aclose is idempotent and closes instances in reverse order; turn_end runs only after the outcome is committed, never after an earlier Stop, and Stop during turn_end makes finalization return the committed Final/Error without rollback. A hook's ask is bounded by the frontend's confirmation timeout, not the hook timeout; result-patch caps apply only to plugin-authored text. Prompt layers are static and capped; command expansions preserve display_text/input_text (the stored display_text is screened by the guardrail too), resolve case-insensitively, pass through guardrails/hooks and never enter the cached system prefix. Plugins execute trusted Python in-process; MCP is deferred.

## Conventions

- Python ≥3.11, `from __future__ import annotations` at the top of every module, full type hints, pydantic v2.
- All I/O-facing code is `async`. Tools are `async def`.
- New tests go in `tests/`; drive the loop with `tests/fakes.py:FakeLLMClient` (scripted, no network). `asyncio_mode = "auto"` is set, so no `@pytest.mark.asyncio` needed.
- Dependency versions in `pyproject.toml` are pinned exactly. Don't loosen them without reason.
- CI enforces `ruff check`, `ruff format --check`, and package-wide `mypy` in both LingCore and LingChat.

## Known gaps (post-MVP)

No domain-specific guardrail implementation ships yet (profiles can load one by
dotted path or the `lingcore.guardrails` entry-point group). Third-party tools now ship through the `lingcore.plugins` entry-point group. MCP
plugin components, subprocess hooks, hot reload and Discord frontends remain deferred. Session resume still
does not restore per-session shell allowlists, and nothing prevents a CLI and a
LingChat process from attaching the same session
concurrently (per-process registry only — a cross-process lease is future
work). Knowledge 1.0 still lacks structured retrieval events/frontend-native
citation rendering, evaluation datasets, a scalable ANN/vector extension for
very large corpora, and the opt-in `auto_retrieve` prompt-injection layer; the
explicit `knowledge` tool remains the retrieval baseline.

Deferred hardening: (1) **Resume
tail hydration** — a session with a valid compaction snapshot now hydrates only
that bounded working set plus the raw post-snapshot tail. A never-compacted
session still loads its full stored history (incl. base64 attachments) before
the first render evicts; bounding that fallback peak needs a block-aware SQL
tail query while independently restoring the lifetime assistant turn count.
(2) **Streaming guardrails** — `post_output` runs only on the final tool-free
turn, so a guardrail can't inspect/transform streamed `TextDelta`s or the
already-shown text; a buffered/guarded streaming mode is a protocol change on
`Guardrail`.
